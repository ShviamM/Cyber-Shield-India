# Netraksh — Android Call-Experience Investigation & Fix Report

**App:** `@workspace/kavach-ai` (Netraksh — India's Digital Bodyguard)
**Scope:** (1) Incoming-call popup not appearing on the lock screen; (2) Post-call scam-reporting experience.
**Hard constraint honoured:** no restricted permissions added — no `READ_PHONE_STATE`, `READ_CALL_LOG`, `READ_SMS`/`RECEIVE_SMS`, `RECORD_AUDIO`, and the app never becomes the default dialer.

> This report is based on a direct review of the actual codebase, not assumptions. Native call behaviour cannot be exercised in this environment (Kotlin only links in an EAS device build), so on-device verification steps are listed at the end.

---

## 1. How the call experience is actually built (as found in code)

**Permissions requested** (`app.json` → `android.permissions`), nothing more:
`POST_NOTIFICATIONS`, `CAMERA`, `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION`, `SYSTEM_ALERT_WINDOW`, `USE_FULL_SCREEN_INTENT`, `ANSWER_PHONE_CALLS`.

**Native (`modules/kavach-screening/android`):**
- `KavachCallScreeningService` is a system-bound `CallScreeningService` holding `ROLE_CALL_SCREENING`. The OS hands every incoming call to `onScreenCall()` **without** any call-log/phone-state permission.
- On each incoming call it **allows the call untouched** (empty `CallResponse` — never blocks/silences), except numbers the user explicitly blocked, which are silently rejected.
- It then launches the caller card two ways: a **direct `startActivity`** of `kavach-ai://call-alert?number=…` (only when "Display over other apps" is held) **and always** a **full-screen-intent notification** (channel `kavach_screening_alerts`, `IMPORTANCE_HIGH`, `CATEGORY_CALL`).
- It **also posts a quiet post-call report notification** (channel `kavach_call_report`, `IMPORTANCE_LOW`, auto-cancel) deep-linking `kavach-ai://report-call?number=…`.

**React (`app/`):**
- `call-alert.tsx` — Truecaller-style caller card. Does the live reputation lookup in JS, and offers **Answer / Block / Report**. Allowed to render even when signed out (`_layout.tsx` exempts the `call-alert` route from the login redirect).
- `report-call.tsx` — one-tap post-call report (pick a call type → submit). Reached from the post-call notification or the call card's Report action.

## 2. Issue #1 — Incoming-call popup not reliable on the lock screen

### Root cause (primary, fixable)
The deep link launches Expo's `MainActivity`, but **the activity was never told to show over the keyguard or wake the screen.** A repository-wide search found **no** `showWhenLocked`, `turnScreenOn`, `setShowWhenLocked`, `FLAG_SHOW_WHEN_LOCKED`, `KeyguardManager`, or `requestDismissKeyguard` anywhere. Consequently, when the full-screen intent (or the direct background start) brings `MainActivity` forward on a locked/off device, the activity is composited **behind the lock screen** and the display is not woken — so the user sees nothing until they manually unlock. This is the core defect.

### Contributing platform factors (not bugs, but gates)
- **Android 14 (API 34) revokes `USE_FULL_SCREEN_INTENT` by default** for apps that aren't the default dialer/alarm clock. The manifest declaration alone is not enough; the app must detect `NotificationManager.canUseFullScreenIntent()` and route the user to the per-app setting. *(Already handled — the code exposes `hasFullScreenIntentPermission` and a `requestFullScreenIntentPermission` flow surfaced in the onboarding SetupGuide.)*
- **Background activity launch** over the lock screen requires `SYSTEM_ALERT_WINDOW` ("Display over other apps"). *(Already requested and surfaced in onboarding.)*
- **OEM battery/autostart managers** (Xiaomi/MIUI, Oppo·Realme/ColorOS, Vivo·iQOO/Funtouch, OnePlus/OxygenOS, Honor·Huawei) can freeze or kill the screening process so `onScreenCall()` never runs. *(Already mitigated — the module opens vendor autostart screens and the battery-optimization exemption settings.)*
- **`POST_NOTIFICATIONS`** must be granted (Android 13+) or the full-screen-intent notification is dropped. *(Already requested.)*

### Fix implemented
Added a local Expo config plugin, **`plugins/withLockScreenCallAlert.js`**, registered in `app.json`, that injects on `MainActivity`:

```
android:showWhenLocked="true"
android:turnScreenOn="true"
```

`showWhenLocked` lets the caller card display on top of the keyguard; `turnScreenOn` wakes a dozing/off display when the full-screen intent brings it forward. Both are **standard activity attributes — no permission, no Play declaration.** The app-level manifest is generated by prebuild, so this must be a config plugin rather than a hand-edited file.

**Verified:** a dry `expo prebuild` confirmed the generated `AndroidManifest.xml` now carries both attributes on `.MainActivity`. (The generated `android/` dir and prebuild's incidental `package.json` edits were reverted afterward — the project stays on the managed prebuild workflow.)

## 3. Issue #2 — Post-call scam-reporting experience

### Root cause
The post-call reporting feature **already exists in the codebase** (`report-call.tsx` + the `kavach_call_report` notification posted by the native service). The perceived absence is explained by:
1. **Build version** — the live test most likely ran an APK built *before* this feature merged. The latest features only appear in a fresh EAS build.
2. **By-design subtlety** — the prompt is `IMPORTANCE_LOW` (no sound, no heads-up) so it doesn't intrude *during* the call. It waits silently in the notification shade, which is easy to overlook.
3. **Android limitation** — there is **no compliant "call ended" callback.** Detecting call end requires `READ_PHONE_STATE` (or `READ_CALL_LOG`), both restricted. `CallScreeningService.onScreenCall()` fires only at *incoming-call* time. So a true "popup after you hang up" is **not possible** without a permission we deliberately refuse.

### Compliant design (what the app does instead)
- A **persistent, quiet post-call notification** is posted at screen-time and survives the call → tap opens the one-tap `report-call` screen with the number prefilled. This is the Play-compliant substitute for a call-ended hook.
- A **Report action on the caller card** (`call-alert.tsx`) lets the user report during/right after the call. **The Issue #1 lock-screen fix also makes this card — and its Report button — usable directly from the lock screen**, which materially improves post-call reporting reach.

### Note / minor UX consideration
Reporting is a write that requires authentication, so tapping the post-call notification while signed out routes to login (by design — anonymous reporting is an abuse risk). Reputation *lookup* on the caller card remains anonymous.

No code change was required for Issue #2 beyond the shared lock-screen fix; the feature is already implemented and compliant.

## 4. Restrictions identified

### Android platform
- No call-ended callback without `READ_PHONE_STATE`/`READ_CALL_LOG`.
- Activities need `showWhenLocked`/`turnScreenOn` to draw over the keyguard and wake the screen.
- `USE_FULL_SCREEN_INTENT` default-revoked on Android 14+ for non-dialer/alarm apps.
- Background activity starts need `SYSTEM_ALERT_WINDOW`.
- Android 15 tightens turn-screen-on behaviour; the full-screen-intent path remains the reliable lock-screen trigger.
- OEM battery/autostart managers can kill the screening service.
- `POST_NOTIFICATIONS` runtime grant required (Android 13+).

### Google Play policy
- `READ_CALL_LOG`, `READ_PHONE_STATE`, `READ_SMS`/`RECEIVE_SMS` are **restricted** — require a Permissions Declaration and carry high rejection risk. **Deliberately avoided.**
- **Default-dialer** path not pursued (heavy policy + UX cost).
- `ANSWER_PHONE_CALLS` is a call-**control** permission (not a restricted call-log/SMS permission) but is call-related and **must be disclosed** at review. It powers the card's Answer/Block actions.
- Caller ID & spam protection must be the app's core, disclosed function — which it is.

## 6. Remaining risks
- **OS-level grants still gate the lock-screen popup.** The fix removes the keyguard/wake defect, but reliable lock-screen display still depends on the user granting overlay + full-screen-intent + notifications and setting a battery-optimization exemption. The in-app SetupGuide drives these, but they are user actions outside the app's control.
- **Lock-screen scope is broader than the call flow (privacy).** `showWhenLocked`/`turnScreenOn` are set on the single shared `MainActivity`, so in principle any launch of that activity while locked could render app UI over the keyguard — not just the caller card. In practice the normal launch path still goes through the keyguard (the launcher is behind it), so exposure is limited to deep-link/full-screen-intent launches (which are the intended call/report screens). A hardening follow-up is recommended: scope the behaviour to the call flow only via a dedicated call-alert activity (or runtime `setShowWhenLocked`/`setTurnScreenOn` toggling around the call-alert lifecycle).
- **Post-call reporting is at-screen-time, not true call-ended** — an Android limitation, not fixable compliantly.
- **OEM variance** — aggressive power managers (especially Xiaomi/Oppo/Vivo) remain the top cause of "popup didn't show"; battery exemption is essential.
- **Untestable here** — native behaviour only runs in an EAS device build; this change is verified structurally (prebuild manifest) and must be QA'd on real hardware.

## 7. Production-readiness assessment
**Code-complete and Play-compliant.** Both features exist in code; the lock-screen defect is fixed at the manifest level with no policy impact. Ready to ship **after** an EAS build and multi-device QA — prioritise one stock-Android device (Pixel, Android 14/15) and the major Indian OEMs (Xiaomi, Oppo/Realme, Vivo, Samsung).

### Verification steps (on a real device)
1. Build: `pnpm --filter @workspace/kavach-ai build:android` (EAS preview APK).
2. Install; open Netraksh → Screening setup; complete the SetupGuide: call-screening **role**, **notifications**, **display over other apps**, **full-screen notifications** (Android 14+), and **battery-optimization exemption** (+ vendor **autostart** on Xiaomi/Oppo/Vivo).
3. **Lock the phone** (screen off), then use **"Send test alert"** — the caller card should wake the screen and appear over the lock screen.
4. Place a **real incoming call** with the app closed/backgrounded — confirm the card fronts on the lock screen.
5. After the call, pull down the shade — confirm the **"Was this call a scam?"** notification; tap it → one-tap report submits.
6. Repeat on each target OEM; confirm the battery exemption is what makes the difference on aggressive devices.
